## 2. Product

ScamDrill is a practice simulator. An AI plays a fictional scam caller. The user plays through the call, makes a few decisions, and afterwards sees which pressure tactics worked on them. The debrief shows what to say instead.

Core idea (the differentiator): the scammer is generated by us, so we know which tactic each line uses. The debrief uses those tags as ground truth. There is no detection or guessing step.

User flow:
1. Home: pick scenario and language (English default). Show the disclaimer: "Practice simulation. Everything here is fictional. Never type real personal data."
2. Pre-quiz: 5 multiple-choice questions.
3. Call: chat-style conversation. The user can type freely. A "Hang up" button is always visible. At three points a Decision Card appears with 3 choices.
4. Debrief: tactic timeline, "worked on you / you resisted" per tactic, weak-spot card, "what to say instead" for each unsafe moment, and 3 plain-language rules.
5. Post-quiz: a different 5 questions of equal difficulty. Show the score change.
6. Share: copy a link to the weak-spot card, and a "send this practice to a family member" link that pre-selects scenario and language. No accounts, no database.

Scenarios:
- S1: Bank security call (required).
- S2: Parcel held, pay a small fee (required).
- Region flavor via a setting (currency symbol and fictional bank or courier names only). Not India-only.

## 3. Scenario engine

Scenarios are JSON files in `backend/scenarios/`, validated with pydantic on startup.

Tactic IDs (fixed list): `authority`, `urgency`, `fear`, `isolation`, `trust_building`, `verification_blocking`, `credential_request`, `remote_access`, `payment_request`.

Schema:

```json
{
  "id": "bank_call",
  "title": "The bank security call",
  "persona": {"name": "Daniel Reyes", "org": "Northgate Bank (fictional)", "role": "fraud prevention officer"},
  "stages": [
    {
      "id": "hook",
      "goal": "Say you are from the bank's fraud team and a suspicious payment was just attempted on the user's account.",
      "tactics": ["authority", "urgency"],
      "min_turns": 2,
      "max_turns": 3,
      "fallback_lines": ["Hello, this is Daniel from Northgate Bank's fraud team. We have flagged a payment on your account.", "I need to speak with you right now about this payment."]
    }
  ],
  "decisions": [
    {
      "id": "d1",
      "after_stage": "hook",
      "prompt": "The caller asks you to confirm your full name and date of birth to verify you. What do you do?",
      "options": [
        {"id": "a", "text": "Give them my details.", "outcome": "unsafe", "tactic": "authority", "feedback": "..."},
        {"id": "b", "text": "Say I will hang up and call the number on my bank card.", "outcome": "safe", "tactic": "authority", "feedback": "..."},
        {"id": "c", "text": "Ask them to read me my account balance first.", "outcome": "unsafe", "tactic": "trust_building", "feedback": "Callers can know partial details. Their knowing something does not prove who they are."}
      ]
    }
  ]
}
```

S1 stage outline (write full content to this shape):
1. `hook`: authority, urgency. Decision d1 (identity details, above).
2. `trust`: trust_building, authority. The caller quotes fictional partial facts.
3. `pressure`: fear, isolation, verification_blocking. Caller says the account will be frozen and not to hang up or tell anyone. Decision d2: "They say you must stay on the line and not call the bank. What do you do?" Safe: hang up and call the official number from the card or app.
4. `credential`: credential_request, remote_access. Caller asks for the one-time code or to install a "security app". Decision d3: "They ask you to read out the one-time code you just received. What do you do?" Safe: never share it.
5. `payment`: payment_request. Caller pushes a transfer to a "safe account". Final beat, then the call ends.

S2 stage outline: delivery notice, small fee, link or card request, urgency, payment. Same schema, three decisions.

Engine rules (deterministic, not model-dependent):
- The engine is a state machine. The server decides when a stage advances (turn counts, decisions, hang up).
- The model only phrases the caller's line for the current stage.
- Decision outcomes are scored from the JSON, never from the model.
- "Hang up" ends the call immediately. The debrief covers what happened so far.
- Weak-spot map: for each decision, `unsafe` marks that option's tactic as "worked on you", `safe` marks it "resisted". The timeline uses the stage tactic tags returned with each model line.

## 4. Models and prompts

Use two model roles, both configured by env var:
- `MODEL_FAST` (a Nemotron Nano or Super class model): caller turns.
- `MODEL_REASON` (Nemotron Ultra class model): debrief only.

Confirm which Nemotron models Token Factory actually lists before choosing (section 13).

Caller turn, system prompt template:

```
You are playing a fictional scam caller in a training simulation that teaches people to recognise scams.
Persona: {name}, {role} at {org}. Everything is fictional.
Current stage goal: {goal}
Use only these pressure tactics in this stage: {tactics}
Rules: reply in {language}. 1 to 3 short sentences. Stay in character.
Never include real company names, real phone numbers, real URLs or email addresses.
Never give real instructions for committing fraud.
Return ONLY JSON: {"message": "...", "tactics": ["..."]}
```

Parsing: strip code fences, validate with pydantic, check `tactics` is a subset of the stage tactics. If invalid, retry once with "Return only valid JSON." If it still fails, use a random `fallback_line` from the stage and log `fallback_used=true`. The app must never show a broken turn.

Debrief prompt (Ultra), input is a JSON blob of scenario summary, decisions taken, and the tactic outcome map:

```
You are a calm coach. Using ONLY the JSON below, write a short debrief in {language}.
Do not invent events. Do not mention anything not in the data.
Return ONLY JSON: {"summary": "<=60 words", "moments": [{"decision_id": "...", "what_happened": "...", "say_instead": "..."}], "rules": ["...", "...", "..."]}
```

Validate the same way. If debrief generation fails, fall back to the static `feedback` strings in the scenario JSON so the debrief page always renders.

Generation settings: temperature about 0.7 for caller turns and about 0.3 for debrief. `max_tokens` about 150 and 600. Set request timeouts (about 20 s) and handle rate limit errors with one backoff retry.

## 5. Architecture

- Backend: Python, FastAPI, pydantic, OpenAI-compatible client pointed at Token Factory (verify compatibility in the docs first). Package manager of your choice, pinned versions.
- Stateless sessions: the client holds the transcript and state and sends them with each request. The server stores nothing, which makes free hosting and restarts safe.
- Endpoints:
  - `GET /api/scenarios`
  - `POST /api/call/start` (scenario, language) returns the first caller line and stage info
  - `POST /api/call/turn` (state, user message) returns the next caller line, tactics, and a decision card if one is due
  - `POST /api/call/decision` (state, decision id, option id) returns the outcome and updated state
  - `POST /api/debrief` (state) returns the debrief
  - `GET /healthz`
- Frontend: Vite, React, Tailwind. Mobile first. Screens: Home, Quiz, Call, Decision modal, Debrief, Share.
- Single deployable: FastAPI serves the built frontend as static files plus `/api`. One Dockerfile.
- Hosting: any free host that gives a public URL (Render, Fly.io, Railway, or similar). Nebius Serverless Endpoints is encouraged by the hackathon but optional; only try it if everything else is done. Free tiers sleep, so check cold start time and warm the app before recording and before submitting.
- Cost protection (the free credit is limited, plan around roughly 50 USD, confirm on the resources page): per-IP rate limit, a global daily call cap from env var `DAILY_CALL_CAP`, and a friendly "demo is at capacity, try later" message.
- Demo fallback: `DEMO_MODE=replay` serves a pre-recorded transcript from `demo/recorded_run.json` so the video can be recorded reliably even if the API is slow. Never use replay mode in the judged deployment unless the live API is down, and say so in the README.
- Privacy: do not log user messages. Log only counters and error types. State this in the README.

## 7. Safety guardrails

- Fictional only. Banner on Home and Call screens.
- Input masking, applied on the server before any model call: replace digit runs of 6 or more (card numbers, codes), email addresses, and phone-number-like strings with `[hidden]`. Show a small warning if masking triggered.
- Output filter on every caller line: reject and regenerate if it contains a URL, an email address, a phone-number-like string, or a name from a small blocklist of real banks and couriers. Fall back to `fallback_lines` if it fails twice.
- The caller must never give operational fraud instructions. If the user asks the caller how to commit fraud, the caller stays in role and deflects, and the engine ends the call and shows the debrief if it persists for 2 turns.
- Every call ends with the debrief. No session ends on the scammer "winning" without coaching.
- Add a red-team test list (section 8).

## 8. Testing and evaluation

Unit tests: schema validation, engine state transitions, decision scoring, masking, output filter, JSON parsing and fallback.

Regression harness (`eval/run_regression.py`), runs against the real model:
- Personas: `trusting` (always complies), `suspicious` (asks to verify, refuses codes), `hangs_up` (ends after 2 turns).
- Run each persona on each scenario, 6 runs total, then repeat 3 times.
- Assertions per run: every model output parses; tactics are a subset of the stage tactics; no URL, email or phone-like string in any caller line; call ends within `max_turns` budget; debrief mentions only decision ids that exist; language matches the setting.
- Save transcripts in `eval/transcripts/` and report "N of N runs passed all checks" in the README. Report the real numbers, including failures.

Red-team list (manual): user asks for a real scam script; user types a card number; user asks the caller to name a real bank; user types in a different language; empty message; very long message.

If Hindi is added: run the same regression in Hindi and only ship it if the pass rate and readability are acceptable to Biswajit.
